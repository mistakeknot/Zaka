# Codex App Server transport

Zaka can keep a Codex App Server process alive across independent CLI invocations.
The protocol follows the [official App Server documentation](https://learn.chatgpt.com/docs/app-server)
and the JSON schemas generated by Codex CLI **0.153.3**.

```bash
session=$(zaka spawn --agent codex --transport app-server \
  --workdir /absolute/project --model gpt-6-astra \
  --sandbox workspace-write --approval-policy on-request \
  --agent-arg=-c --agent-arg=model_reasoning_effort=xhigh \
  --agent-arg=-c --agent-arg=service_tier=Standard \
  --metadata-json '{"route_id":"parent-owned-value"}')

zaka steer "$session" "Inspect the task and ask any needed questions."
zaka status "$session" --json
zaka questions "$session" --json
zaka answer "$session" --request-id 42 \
  --answers-json '{"question_id":{"answers":["Selected option or free text"]}}'
zaka kill "$session"
```

## Parent interface

- `spawn` prints only a generated `as-<24 hex digits>` handle after successful
  `initialize`, `initialized`, and `thread/start`. It starts no turn. Readiness
  means the thread exists, not that work completed or model access was proven.
- App Server requires an explicit model, sandbox (`read-only` or
  `workspace-write`), and approval policy (`untrusted`, `on-request`, or `never`).
  The installed schema no longer accepts the old `on-failure` string.
- App Server `--agent-arg` accepts repeated `-c`, `key=value` pairs for
  `model_reasoning_effort` and `service_tier` only. Effort is preserved exactly;
  `Standard` maps to `default`. Other overrides, profiles, `--name`, and
  `--permission-mode` are rejected for this transport. The effective thread
  model, effort, service tier, cwd, sandbox mode, and approval policy are checked
  against the request before reporting readiness. Approvals route to `user`.
- `--metadata-json` is opaque JSON, retained under `config.metadata`. Zaka does
  not interpret it, send it to Codex, or change the parent's route decision.
- `steer` starts the first/next turn, or sends `turn/steer` with the active
  `expectedTurnId`. Success prints a JSON status snapshot acknowledging the RPC.
  A stale-turn or policy error is surfaced without retry or model substitution.
- `status --json` and `questions --json` return the same complete status object.
  `pending_requests` contains raw request IDs, methods, structured params, and
  `answered`. Numbers and strings retain their JSON types. For a string ID that
  collides with a numeric ID, pass its quoted JSON representation.
- `answer --answers-json` takes the **question-ID map**, not the outer protocol
  response. Zaka wraps it in `{"answers": ...}` and replies using the original
  server request ID. Every question must be present; unknown IDs, malformed
  values, duplicate submissions, and resolved requests are rejected. An answered
  request stays visible until `serverRequest/resolved`, including remote cleanup.
- Only `item/tool/requestUserInput` can be answered. All other server requests,
  including execution, file, permission, and MCP approvals, park visibly as
  `blocked-approval`. There is no approval-granting API in this implementation.
  Nonblocking user-input requests remain visible while the turn runs.
- This transport explicitly enables Codex's experimental
  `default_mode_request_user_input` feature so execution-mode agents can ask
  structured questions. It does not modify the user's base configuration or
  enable experimental context management. Revalidate this flag when upgrading
  Codex; protocol mocks alone cannot prove that the model receives the tool.

Example status shape (values abbreviated):

```json
{
  "session": "as-00112233445566778899aabb",
  "transport": "app-server",
  "thread_id": "thread-id",
  "turn_id": "turn-id",
  "turn_status": "inProgress",
  "phase": "waiting-input",
  "pending_requests": [{
    "id": 42,
    "method": "item/tool/requestUserInput",
    "params": {"questions": [{"id": "question_id", "question": "Which?"}]},
    "answered": false
  }],
  "event_log": "/home/user/.local/state/zaka/as-00112233445566778899aabb/events.jsonl",
  "config": {"metadata": {"route_id": "parent-owned-value"}},
  "worker_pid": 1234,
  "updated_at": "2026-09-04T00:00:00Z"
}
```

Phases: `starting`, `ready`, `starting-turn`, `running`, `waiting-input`, `blocked-approval`,
`completed`, `interrupted`, `error`, `disconnected`, `stale`, and `killed`.
`error` carries the failure text when present. A failed turn is never completed.

## Persistence and lifetime

The detached Zaka worker owns Codex stdio and a private Unix control socket.
State defaults to `~/.local/state/zaka`; `ZAKA_STATE_DIR` selects an isolated
location. Existing state roots must be private directories. Long socket paths
are rejected with a request to select a shorter state root.

Session directories use mode 0700. Atomic `state.json`, `config.json`, the
append-only, flushed `events.jsonl`, stderr logs, and sockets use mode 0600.
The event log includes incoming and outgoing protocol messages. Consumers can
tail it for assistant output and use snapshots for current requests and phase.

Startup is bounded to 20 seconds; protocol operations to 8 seconds; local
control connections to 16 seconds. Up to 16 control handlers run concurrently,
mutations serialize with cancellation, and the protocol reader continuously
processes events. A timeout with an uncertain RPC outcome disconnects the
session instead of retrying it. Disk and transport failures stop the connection.

`kill` waits for normal Codex process-group and socket cleanup, retaining logs,
metadata, and pending-request evidence. If the worker has already died, it
cleans the stale endpoint without signaling a PID read from disk. A worker crash
or restart of the machine does not automatically resume a thread or replay
pending answers; status reports the preserved session as stale/disconnected.
Recovering those sessions via `thread/resume` is outside this interface.

Legacy agents retain tmux transport. The default Codex tmux command is now the
interactive `codex` CLI, and `Config.PermissionMode` maps to `--sandbox` (for
example `read-only` or `workspace-write`). With no mode, Codex uses its normal
configuration. Zaka no longer adds `exec` or a permission-bypass flag.

## Verification

The test suite uses in-memory JSON-RPC peers and detached mock subprocesses,
including separate CLI invocations. It does not use live credentials or model
calls. A separate manual probe of installed 0.153.3 used an empty temporary home,
file-only credential storage, and stopped after `thread/start`; it confirmed
the handshake and exact Astra/xhigh/default settings without starting inference.

```bash
go test ./... -count=1
go test -race ./... -count=1
go vet ./...
go build ./cmd/zaka
```

On restricted hosts, the mock worker tests need permission to bind local Unix
sockets. No network access is required by the tests. Live Astra inference,
parent routing integration, and installation remain the parent integrator's work.

### Live verification, 2026-09-05

The parent integrator built this checkout and exercised a real ChatGPT-authenticated
Astra/high/Standard session on Codex 0.153.3 with `read-only` and `on-request`.
The first turn emitted `item/tool/requestUserInput`, accepted a structured BLUE
answer, cleared the request, and completed with `ROUNDTRIP_BLUE`. A second turn
on the same thread accepted `turn/steer` while a question was pending, then
completed with `STEERED_YES` after its YES answer. Killing the worker retained
queryable status and evidence. These are protocol probes, not accepted software
tasks or a completed estate canary.

The sanitized [protocol evidence](astra-app-server-canary.json) includes the
requests, resolution events, steering input with its expected turn ID, and final
answers. No credentials or unrelated transcript material are included.
